# Host Simulation (host_sim) — Fast Feedback on macOS

This directory contains a native (non-Zephyr) simulator that runs the **real firmware logic** from the water pump project on your laptop.

It links the actual C files:

- `app/src/flow_processor.c`
- `app/src/pump_state_machine.c`

and feeds them pulse period traces generated by the Python `FlowPlant` continuous model.

This is currently the **recommended daily development workflow** on macOS because:

- `native_sim` (Zephyr's fast emulation) is Linux-only.
- Full qemu_x86 + gpio_emul tests are slow for long plant traces.
- This gives you near-instant iteration while still exercising the exact same processing and state machine code the device will run.

## Quick Start

```bash
# 1. Generate a realistic trace from the plant model
cd ../plant
python generate_pulse_train.py --scenario watering --duration 40 \
       --output-csv ../../model/sim/plant_trace.csv

# 2. Build and run the simulator
cd ../sim
make
./host_sim plant_trace.csv
```

Or even shorter:

```bash
cd model/sim
make demo
```

## Supported Trace Formats

The loader is flexible and accepts:

- The CSV format produced by `generate_pulse_train.py` (recommended):
  ```
  time_s,period_us
  0.0,10000000
  0.02,2510014
  ...
  ```
- Simple space or comma separated lines (`t [flow] period`)

## What It Simulates Today

- Real median + 1.5× outlier rejection + flow rate calculation via `flow_processor`
- Real `pump_state_machine` transitions
- Pump on/off via shims
- Feedback relay clicks

## What It Does NOT Simulate (Yet)

- Full `PumpService` reconciliation logic (timer + flow + safety)
- Actual Zephyr threads / zbus publication timing
- Real driver ISR timing jitter

We can gradually pull more pure logic into the simulator as it gets extracted from the services.

## Flow Stabilization Contract Fidelity (Phase 1 — host_sim only)

The main simulation loop has been updated (host_sim.c) to faithfully reproduce the *usage* of the original flow analyzer from the master branch `pump_controller_thread`:

- Phase-aware K-factor (INITIAL_K=2.0 while conceptually "off" for the first low-flow plateau, NORMAL_K=3.0 while "on")
- Explicit `flow_analyzer_core_init` (reset) immediately after every confirmed plateau (prevents carry-over "generous" detections)
- First sample after reset always returns false
- Dynamic 1.5× `latest_plateau_period` watchdog timeout while "on" (triggers conceptual off + full reset)
- Rich per-sample trace showing diff_count, noise, K in use, phase, and reset count

Run against the realistic 20 s scenario:

```bash
cd model/sim
./host_sim 20s_realistic_trace.csv
```

The output now makes the "wait for several samples + disciplined reset" behavior visible and matches the contract described in the approved plan.md.

**Phase 2 update**: The contract logic now lives in the pure reusable module `app/src/pump/flow_stabilization_contract.c` (and header). `host_sim` calls it directly — this is the single source of truth. Pump demand path in the sim is still disabled pending user direction.

## Common Workflows

### Iterate on the plant model + firmware reaction

```bash
# Edit parameters in flow_plant.py or generate_pulse_train.py
python generate_pulse_train.py --output-csv ../../model/sim/plant_trace.csv
make -C ../sim run
```

### Try different scenarios quickly

```bash
python generate_pulse_train.py --scenario variable --duration 60 \
       --output-csv ../../model/sim/trace_variable.csv
./host_sim trace_variable.csv
```

## Building Manually (if you prefer)

```bash
gcc -I../../app/include -I../../app/src \
    host_sim.c host_shims.c \
    ../../app/src/flow_processor.c \
    ../../app/src/pump_state_machine.c \
    -o host_sim -lm
```
